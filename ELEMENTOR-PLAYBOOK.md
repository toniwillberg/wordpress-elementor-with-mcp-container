# WordPress + Elementor MCP Build Playbook

Field notes for AI agents (opencode and friends) building sites on this stack.
Written by opencode (AI) on Sep 24 2026 building a test site on WordPress and Elementor site build.
Environment: WordPress 7.1.2, Elementor 4.3.0 (atomic/v4), Hello Elementor theme, emcp-tools 3.17.1 MCP, Elementor MCP adapter (in-plugin), Docker Compose (site at http://localhost:8080, wpcli service).

Everything below was learned the hard way. Read this before building pages; it prevents repeated mistakes.

## 1. Which tool for which job (the tool map)

| Task | Use | Do NOT use |
|---|---|---|
| Create pages, build/modify page content (atomic v4) | **mcp-adapter**: `elementor/create-page`, `elementor/build-composition`, `elementor/manage-elements`, `elementor/update-page-settings`, `elementor/publish-document` | emcp element tools for bulk page work (they flip published pages to draft) |
| Global CSS classes + design tokens (variables) | **mcp-adapter**: `elementor/manage-classes`, `elementor/manage-global-variable`, `elementor/manage-default-styles` | raw CSS in JS widgets when a class can do it |
| Themer header/footer templates (the `emcp_theme_template` CPT) | **emcp-tools element tools**: `add-flexbox`, `add-div-block`, `add-atomic-*`, `batch-update`, `add-custom-js` | **mcp-adapter build-composition — it silently does NOT persist on this CPT** (reports success, writes nothing) |
| Kit (Global Colors/Typography) settings | **mcp-adapter** `elementor/update-page-settings` on the kit post (option `'elementor_active_kit'`, here ID 4) — ONE comprehensive call | emcp `update-global-colors` / `update-global-typography` (their writes get lost and they read stale data) |
| Posts of custom post types, slugs, post status, front page | **wpcli**: `docker compose run --rm wpcli wp ...` | emcp `create-post` (rejects custom CPTs), emcp `update-post` slug param (silently fails) |
| Client-side interactivity (quiz logic, live filtering, simulated checkout) | **emcp-tools**: `add-custom-js` (HTML widget, free-Elementor compatible) | trying to force Elementor widgets to do stateful logic (no free component exists) |
| Fetch rendered page HTML for QA | `curl` from bash | emcp `get-page-html` (fails "Only published posts…" even on live pages) |

## 2. Golden rules (violating these cost hours)

1. **Order: ALL Elementor/emcp edits first, wpcli slug/status fixes LAST.**
   Every Elementor save can reset `post_name`, `post_parent`, and even flip pages to **draft**.
   Final step of every page: `wp post update <id> --post_name=<slug> --post_parent=<parent> --post_status=publish && wp rewrite flush`.
2. **One owner per data domain.** Kit settings via the adapter only. Themer templates via emcp only. Do not mix emcp global-settings tools with adapter kit writes — the adapter's kit `update-page-settings` **REPLACES** `_elementor_page_settings` wholesale, wiping anything written before (including emcp's writes).
3. **Never mix `manage-elements` and `build-composition` on the same published document without publishing in between.** They stage to the same autosave and silently overwrite each other (a full rebuild was lost this way; symptom: build reports success, live tree unchanged, version timestamp looks stale). Pattern: stage → publish → verify → next tool.
4. **Publish after every adapter edit on a published page.** Adapter edits go to a staged autosave; `elementor/publish-document` promotes them. `publish-document` lies about `previous_status` — always verify with `wp post list` or curl, never trust its response.
5. **Global class labels ARE the CSS class names.** Kebab-case only (`sitename-nav-bar`), lowercase, no spaces. A label like "DTV Nav Bar" renders `class="DTV Nav Bar"` (3 broken classes) and emits dead selectors.
6. **Themer header/footer only render on the DEFAULT page template.** Canvas strips `get_header()`/`get_footer()`, so the Hello-adapter injection never fires. Design-wide chrome via Themer ⇒ pages use `template: "default"` + `hide_title: "yes"` (kills the theme's `<h1 class="entry-title">`).
7. **Elementor CSS files regenerate lazily.** After kit/class changes, other pages' CSS files get purged and reappear on their next visit. Don't panic-grep an empty css dir; curl the page first.
8. **Custom code must carry a header** (project rule): what it is, what it does, `Generated by <agent> (AI) — not hand-written`, date. Applies to PHP, JS widgets, mu-plugins.

## 3. Build sequence for a new site (the recipe that works)

1. **Plan → get user approval** (structure first, visuals later — project rule).
2. **Kit** (one comprehensive adapter `update-page-settings` on the kit ID): `system_colors` (4), `system_typography`, `custom_colors` palette, `body_background_color`, `body_color`, `body_typography_font_family`, link colors, h1-h6 colors, button defaults, `mobile_browser_background`. Verify via `wp post meta get <kit> _elementor_page_settings --format=json` — never via emcp `get-global-settings` (stale).
3. **Variables** (adapter `manage-global-variable`): brand colors/fonts as `--label` CSS vars. Labels lowercase with dashes. Font value = single Google family name, no stacks.
4. **Default tag styles** (adapter `manage-default-styles`): body/h1-h6/p/a (NOT `body` — invalid tag; body bg comes from the kit). These also style JS-rendered markup — big lever.
5. **Global classes** (adapter `manage-classes`): every repeated style becomes one kebab-case class. Supported in class css: plain declarations, `&:hover/&:focus/&:active`, `@media(--mobile)` etc. NOT supported: `&[attr]` selectors (leak raw — put state-dependent styling in a separate class attached by JS).
6. **Themer templates** (emcp): `create-theme-template` (free quota: 1 per type) → build with emcp `add-flexbox`/`add-atomic-*` → `batch-update` to attach classes (`settings.classes = {"$$type":"classes","value":["g-xxxx"]}`) + `editor_settings.title` labels → `add-custom-js` if needed → conditions auto-seed `entire-site` (verify `resolve-template`). Set `_elementor_edit_mode` meta to `builder` (wpcli) if the renderer sees empty output.
7. **Pages** (adapter): `create-page` → `update-page-settings` (`template`, `hide_title`) → `build-composition` (one call per page: XML + element_config + style, classes by label, hover/`@media(--mobile)` inline) → publish.
8. **JS widgets** (emcp `add-custom-js`): self-locating marker pattern (§5).
9. **wpcli cleanup** (THE LAST STEP): slugs, parents, statuses, `page_on_front`, `wp rewrite flush`.
10. **Verify** (§6), then hand URLs to the user. Never touch an existing live page without preview-approval (project rule).

## 4. Tool quirks catalog (bugs found, workarounds that work)

**mcp-adapter (Elementor 4.3 MCP module):**
- `list-widget-schemas` / `get-widget-schema` throw `Controls_Stack::sanitize_settings(): Argument #1 must be array, null given`. Workaround: learn prop shapes from `build-composition` warnings + `get-page-structure include_content=true` (settings + `default_styles` show the base CSS layer).
- `update-page-settings` on the kit REPLACES all settings (claims "merged"). Do one comprehensive call; re-verify with wpcli meta.
- Edits on published docs stage to an autosave; always `publish-document` after.
- `build-composition` on the Themer CPT writes nothing (silent success). Use emcp tools there.
- `manage-elements` `style` MERGES only — it cannot remove old inline declarations. To strip duplicated inline styles, rebuild the subtree (`build-composition` with `mode: "replace_children"` — publish IMMEDIATELY after, see rule 3).
- Empty-string style (`style: ""`) is ignored, not a clearing operation.
- The staged-autosave publish promotion does NOT fire `elementor/document/after_save` on the live document → stale class-usage metas + stale atomic CSS (pages render missing class styles). Fix: see the CRITICAL post-edit step in §5.

**emcp-tools:**
- Element edits (`add-*`, `remove-element`, `batch-update`, `add-custom-js`) on PUBLISHED pages can flip them to **draft** and reset slug/parent. Always re-publish + wpcli fix after (rules 1 and 4).
- `delete-post` resets `show_on_front`/`page_on_front` when trashing a page it resolves as front. After ANY `delete-post` of a page: re-apply `wp option update show_on_front page && wp option update page_on_front <id>`.
- `get-global-settings` returns a stale pre-rebuild snapshot. Ground truth = `wp post meta get <kit> _elementor_page_settings --format=json` + generated CSS.
- `get-page-html` refuses published pages. Use curl.
- `create-post` rejects public CPTs ("not a writable post type") — use wpcli for CPT entries.
- `update-post` slug changes silently fail — use wpcli.
- `get-widget-schema` full:true errors for atomic widgets; the curated catalog covers only v3 widgets.
- `save-as-template`/`apply-template` insert COPIES (not linked instances) — for site chrome use Themer templates instead.

**Elementor v4 rendering facts:**
- `e-button` base = blue (#375EFB), 12px/24px padding, radius 2. `e-flexbox` base = `padding:10px; flex-direction:row`. ALWAYS override these explicitly on every button/flexbox.
- `e-heading` accepts only h1-h6 tags; for text spans use `e-paragraph`.
- Atomic element CSS lives in `local-<id>-frontend-*.css` / `global-<id>-frontend-*.css`, NOT `post-<id>.css` (which stays ~empty).
- Class-attached element CSS emits per-page `global-*.css` files keyed by the pages using them.
- Known cosmetic bug: class css fallback declarations emit a trailing literal `\n` before `}` (harmless — browsers discard it in error recovery).
- Widget local styles from emcp's `settings.styles` must be fully typed (`{id,label,type:'class',variants:[{meta:{breakpoint,state},props:{prop:{$$type,value}}}...]}`) — half-shapes silently break. Prefer global classes and avoid local styles entirely.

## 5. Recipes

**CRITICAL post-edit step — re-fire `after_save` or pages render unstyled:**
The adapter's staged-autosave publish promotion and emcp's meta-level element writes do NOT fire `elementor/document/after_save` on the live document. Result: the frontend `_elementor_used_global_class` metas (which drive the per-page global-class CSS files) and the atomic CSS cache go stale — pages keep rendering with missing class styles (buttons default blue, kit-default font sizes, borderless cards) even though the HTML has the right class names. After any structural Elementor edit round, run for every edited page/template id, then curl the page to trigger CSS regeneration:
```
docker compose run --rm wpcli wp eval "do_action('elementor/document/after_save', \Elementor\Plugin::\$instance->documents->get(<ID>), []);"
```

**Visual QA harness (all containerized, in ./qa/):**
- `docker compose run --rm qa-browser sh -c "npm install --no-progress && node capture.js && node audit.js"` — screenshots of every live screen + the design prototype (desktop/mobile, full-page) and side-by-side composites, plus a computed-style audit against the design tokens. Results: `qa/report.html` (open in a browser), `qa/audit.md`, `qa/shots/`.
- Both scripts run a **connectivity preflight first and refuse to screenshot if any screen is unreachable** — never skip it (learned the hard way: a full screenshot run captured only "qa proxy error" text).
- Docker networking facts: the WordPress container listens on **port 80** internally (`8080:80` is only the host mapping), and `network_mode: host` (works on Docker Desktop) lets a containerized browser reach `http://localhost:8080` exactly like the host — no proxy needed. The old in-container HTTP-proxy approach is retired.
- Interactive QA via **Playwright MCP** (service `playwright-mcp`, image `mcr.microsoft.com/playwright/mcp`): `docker compose run --rm -T playwright-mcp` serves MCP over stdio; configured in `opencode.jsonc` (`.mcp.json` for other clients) as server "playwright". Browser flags live in the compose `command` (headless, isolated, output-dir /work/shots). **Requires an opencode restart** to load. The design prototype is reachable inside it at `file:///work/import/…`.

**Self-locating JS widget** (works in pages AND Themer templates — no fragile ids):
```js
/* <MARKER_NAME> + AI-generated header comment (see rule 8) */
(function () {
  var script = [].slice.call(document.querySelectorAll('script'))
    .filter(function (s) { return s.textContent.indexOf('<MARKER_NAME>') > -1; })[0];
  if (!script) return;
  var mount = script.closest('[data-e-type="e-div-block"]'); // or e-flexbox
  // ... build/render inside mount; discover siblings via mount.parentElement
})();
```
Send with `wrap_dom_ready: true`. Verify with: extract script from curl'd HTML → `node --check`.

**Custom post type + REST for dynamic sections** (when no Pro Loop Grid):
- Mu-plugin (in `wp-content/mu-plugins/`, inside the project): `register_post_type` with `'show_in_rest' => true`, taxonomies likewise, meta via `register_meta('post', 'key', ['object_subtype' => 'cpt', 'show_in_rest' => true])`. ACF free does NOT expose fields via REST (Pro only) — use native meta + ACF local field group bound to the same keys for admin UI.
- REST fields appear under the **rest_base** (e.g. `provider-categories`), not the taxonomy name.
- Front-end: JS fetches `/wp-json/wp/v2/<rest-base>`, renders cards, filters client-side. Feature images come from `_embed=wp:featuredmedia` (absent when unset — try/catch).

**Themer header/footer with current-page highlight:**
- Global classes `sitename-nav-link` (base+hover) and `sitename-nav-link-current` (color only).
- Tiny JS in the header template compares `location.pathname` with each link's URL; on match sets `aria-current="page"` AND `classList.add('sitename-nav-link-current')`.
- **Required mu-plugin hook** (already in `wp-content/mu-plugins/sitename-providers.php`): Themer parts render mid-page, AFTER Elementor's atomic-styles collection, so their CSS never enqueues. The hook fires `do_action('elementor/post/render', <slot ids>)` at `wp_enqueue_scripts` priority 19. Without it, Themer parts render UNSTYLED.

**Front page swap:**
```
wp option update show_on_front page && wp option update page_on_front <id> && wp rewrite flush
```
Expect `/dtv/`-style permalinks of the front page to 301 to `/`. Link nav "home" to `/`.

## 6. Verification checklist (per page, via curl + python/grep — not emcp reads)

1. HTTP 200 on every URL; `/` serves the front page; sub-page slugs resolve (404 = slug reset happened → re-run wpcli fixes).
2. Exactly ONE `sitename-nav-bar` and ONE `sitename-footer-bar` (or your equivalents) — no doubled chrome, no theme `site-title`, no "All rights reserved".
3. No `entry-title` (theme page title leaked = `hide_title` missing).
4. Fonts: `family=<YourFont>` present in google fonts links; old fonts gone.
5. All class names present in HTML AND their CSS in `global-*/local-*` files with valid selectors (no spaces in class names).
6. JS markers present once per widget; extract + `node --check` after any JS change.
7. REST endpoints return data (`curl /wp-json/wp/v2/<rest-base>`).
8. `wp post list --post_type=page --fields=ID,post_name,post_parent,post_status` — everything publish, slugs correct.
9. Kit CSS regenerated and contains your variables (`--e-gv-` / label vars in `post-<kit>.css`).
10. Media/others untouched; user approval before replacing existing live pages.
11. Design-fidelity QA: run the visual harness (§5) — computed-style audit should pass 100%, then eyeball the side-by-side composites in `qa/report.html` against the prototype.

## 7. Reproducibility & new deployments

- **Deployment model: this scaffold is fired once per website.** A new project = a fresh copy of this project folder (or git clone once versioned) + `docker compose up`. wp-setup installs WordPress, the plugins from `WP_PLUGINS` (wordpress.env), and the theme; `wp-content/mu-plugins/` ships in the repo and loads automatically. Site content (pages, kit, classes, templates, providers) is **built fresh by an agent** following §3 — it is never restored from a dump, so this playbook IS the source of truth: every hard-won step (ordering rules, the after_save re-fire, wpcli slug fixes) must stay in it.
- **Repo-shipped vs runtime:** committed = compose/env files, instructions, `qa/` scripts + package-lock, `import/` (design reference), `wp-content/mu-plugins/`. Ignored/regenerated = `wp-content/{plugins,themes,uploads,upgrade}` (wp-setup installs them), `qa/node_modules`, shots and reports. Install QA dependencies with `npm ci` (uses the committed lockfile).
- **QA harness is per-site configuration:** for a new project, edit the `PROTO` path and `SCREENS` list at the top of `qa/capture.js`, and replace the `PROBES` table in `qa/audit.js` with expectations derived from that project's design export. The harness itself (preflight-first capture, composites, computed-style audit, Playwright MCP service) is reusable as-is.
- **Version drift:** plugin auto-updates are enabled by owner choice, so Elementor drifts past the version this playbook's bug catalog was validated against (see header). After any major plugin update, re-run `node audit.js` — a passing 100% audit is the drift alarm.

## 8. Upstream bugs worth reporting (observed on Elementor 4.3.0 / emcp-tools 3.17.1)

- Adapter schema tools fatal (§4). Adapter publish misreports status. Adapter build-composition silently no-ops on `emcp_theme_template`.
- emcp stale `get-global-settings`; `get-page-html` rejects published pages; CPT rejection in `create-post`; silent slug failures in `update-post`; draft-flip on element edits; front-page option reset in `delete-post`.
- Elementor: Themer parts unstyled without the enqueue-timing hook; class-css `\n` artifact; label-with-spaces classes emitted broken (should be validated kebab-case at creation).
