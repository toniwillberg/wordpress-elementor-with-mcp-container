# Project Notes

- **READ `ELEMENTOR-PLAYBOOK.md` (project root) BEFORE any WordPress/Elementor site work.** It contains the tested build sequence, the tool map (which MCP tool for which job), and a catalog of tool bugs with workarounds learned during the DTV build (Sep 2026). Violating its ordering rules breaks slugs, statuses and styling.

- never write any files on my filesystem outside the project folder. If you need temporary folder, use one inside the project.
- if you are going to do something that probably takes a bit longer time, remember to tell the user what you are going to do so he knows it will take a longer time

- you can setup and use Playwright MCP to do QA for the site you are building
- when you take screenshots or export HTML or other stuff from the site for QA purposes, always use timestamp in the filenames so you known later they are relevant to the current session. Also consider when is appropriate time to clean up the QA shots folder
- for visual QA use the containerized harness in `qa/` (see ELEMENTOR-PLAYBOOK.md §5) or the `playwright` MCP server. Always let the connectivity preflight run — never screenshot against an unreachable site. QA artifacts (`qa/shots/`, `qa/report.html`) are regenerated by the scripts, never hand-edited
- after any structural Elementor edit round, re-fire `elementor/document/after_save` for the edited documents (playbook §5) or pages render with stale/missing class styles
- clean up Docker containers that are no longer needed (e.g. stale `wpcli-run-*` MCP adapter containers left over from previous sessions): check `docker ps` and `docker rm -f <name>` anything not part of the active compose stack or current MCP session

## Site
- The site is built with **Elementor** (atomic elements supported, v4.x). Always build/modify pages with the Elementor tools (containers, atomic widgets), not Gutenberg blocks.
- Always use the **Elementor MCP tools** (emcp-tools) or **MCP adapter** (mcp-adapter) for any site work if those can do the task. If you need to do something else, tell user that you are doing it.
- WHen user asks to edit an existing page, always create a preview page first, then ask user to approve the review before overwriting the original page
- never suggest to use Elementor Pro unless the site has Elementor Pro license
- you can use docker compose and wpcli to install plugins
- use Elementor components if available, then fall back to Elementor Addons or other installed stuff - avoid creating custom HTML or CSS to create visual elements if suitable component exists
- try to use all related capabilities of the provided MCPs when building the site
- do not generate media without asking user's permission first
- if you need to create a temporary page, name it accordingly and tag it as (MCP)
- if you need additional WordPress plugins, only suggest free plugins unless user asks commercial ones
- ask user if he wants to enable auto-updates for all plugins in WordPress
- when you build a site, focus first on the site structure, pages, hierachy; and only after the whole site is setup then go on to fine tune the visual details
- use templates, components, themes and styles when feasible instead of doing any HTML/CSS hacks for individual parts of the site
- remember that a human webmaster will be updating and administering the WordPress site, use names that are human readable and consider best practises for site maintainability and normal operations
- if you write PHP, Javascript or other code (excluding HTML), remember to add human-readable description telling what the code is for, what it does and that it was generated instead of written by a human
